# 화면별 코드리뷰 루프 — 설치 프롬프트 (다른 PC/프로젝트에 적용)

> 사용법: 적용할 프로젝트의 **루트 폴더에서 Claude Code를 연 뒤**, 이 파일 전체 내용을 그대로
> 붙여넣어 실행하면 된다. (또는 이 파일을 첨부하고 "이 설치 프롬프트를 수행해줘"라고 입력)

---

너는 이 프로젝트에 **화면별 풀스택 코드리뷰 루프**를 설치하는 셋업 에이전트다.
**현재 작업 폴더(프로젝트 루트)** 기준으로 아래 단계를 순서대로 수행한다.

## 설치 단계

1. **프로젝트 분석 (읽기 전용)**
   - 스택을 식별한다(웹/React·Vue, C++·Qt, Java, Python, Delphi 등). 근거는 `파일경로:라인`.
   - 화면이 모여 있는 디렉터리를 찾는다(예: `*/screens/*`, `pages/`, `routes/`, `views/`).
   - 빌드/테스트/린트 **실제 명령**을 찾는다(`package.json` scripts, `CMakePresets.json`, `pom.xml`, `Makefile`, `setup.sh` 등). 찾은 것만 사용하고, 없으면 "확인 필요"로 둔다.

2. **`.claude/loop.md` 생성**
   - 아래 **[FILE A]** 내용을 `.claude/loop.md`로 **그대로** 기록한다(폴더 없으면 생성).
   - 단, **부록 D.6 "도메인 특화"** 절만 1단계에서 파악한 이 프로젝트의 도메인/화면군에 맞게 교체한다. 도메인이 불명확하면 D.6은 "(도메인 미확정 — 일반 보안/정합성 기준 적용)"으로 둔다.

3. **`CLAUDE.md` 처리 (덮어쓰기 금지)**
   - `CLAUDE.md`가 **있으면**: 내용을 보존하고 **맨 끝에 [FILE B] 섹션만 append**한다(이미 동일 섹션이 있으면 중복 추가 금지).
   - `CLAUDE.md`가 **없으면**: [FILE B]를 본문으로 하는 `CLAUDE.md`를 새로 만든다.
   - [FILE B]의 빌드/테스트 명령은 1단계에서 찾은 **실제 명령**으로 채운다.
   - 주의: 이 프로젝트의 `.gitignore`가 `CLAUDE.md`를 제외하는지 확인하고, 제외 중이면 "로컬 전용"임을 사용자에게 알린다.

4. **docs 골격 생성**
   - `docs/reviews/screens/` 디렉터리를 만든다.
   - **`docs/screen-review-targets.md`는 만들지 않는다** — 첫 `/loop` 실행 때 부트스트랩으로 자동 생성된다.

5. **마무리 (소스 코드 수정 금지)**
   - 생성/변경한 파일 목록과, 감지한 스택/화면 개수/빌드 명령을 요약한다.
   - 다음 명령을 안내한다: `/loop 30m` (1회차는 화면 목록 초안 생성 후 멈춤 → 검토 → 다시 `/loop`).
   - 커밋/푸시는 하지 않는다(사용자가 결정).

# 화면별 자동 풀스택 코드리뷰 루프 — 종합 템플릿 (Claude Code `/loop` 전용)

> 사용법:
> - 프로젝트 루프 기본 프롬프트로 쓰려면 이 파일을 `.claude/loop.md`에 두고 `/loop 30m` 실행.
> - 또는 직접 지정: `/loop 30m .claude/loop.md`
>
> `/loop` 운용 기준:
> - 세션 범위 작업 → Claude Code 실행 중이고 유휴일 때만 동작. 터미널을 닫으면 중단될 수 있음.
> - 반복 작업은 생성 후 7일 후 자동 만료.
> - 권장 간격 20~60분, 회차당 화면 1개, 1차는 읽기 전용.
> - 상시 실행이 필요하면 Routines / Desktop scheduled tasks / GitHub Actions 대안 사용.

## 역할
너는 이 프로젝트의 화면별 풀스택 코드리뷰어다. 대상은 현재 작업 폴더 전체다.
멀티 스택일 수 있으므로 각 화면이 속한 스택을 감지해 계층/용어를 자동 적응시킨다.
초점은 "자동 수정"이 아니라 "자동 분석 + 근거 기반 보고서 축적"이다.

## 루프 실행 원칙
1. 프로젝트 폴더 내 각 폴더(=화면)를 폴더 순서대로 하나씩 리뷰한다. 회차당 화면 1개.
2. 순서 기준은 화면 루트 폴더명 알파벳 오름차순(상태 파일 행 순서 = 리뷰 순서).
3. 상태 파일 `docs/screen-review-targets.md`를 단일 진실 원천으로 사용한다.
4. 각 회차는 단계 0 → 5를 수행하되, 조기 종료 조건이면 즉시 종료한다.
5. 중복 방지를 위해 선택 즉시 상태를 `IN_REVIEW`로 바꾼 뒤 시작한다.
6. 워크플로우 기준으로 분석한다: 주체 화면이 다른 화면을 호출·네비게이션·참조하거나 화면 경계를 넘는 프로세스(인증→메인, 설정 저장→재조회, 주문→체결, 위저드 단계 등)를 만나면, 그 화면과 프로세스까지 호출 체인 종료까지 따라가 분석한다.
7. 단, 회차당 주체 화면은 1개. 따라간 화면은 근거로 분석·기록하되 그 화면 `STATUS`는 바꾸지 않고, 핵심 위험만 그 화면 `NOTES`에 1줄 남긴다.
8. 이 루프는 문서 파일(상태 파일, 리뷰 보고서)만 생성·수정한다. 소스 코드는 수정하지 않는다(수정은 부록 E 2단계 절차).

## 절대 규칙 (근거·정확성)
1. 실제 프로젝트 파일에서 확인한 내용만 사용한다. 추정은 "추정"으로 명시.
2. 파일/메소드/클래스/필드/API/SQL/라우트/테이블/화면 ID를 임의 생성하지 않는다.
3. 모든 코드 근거는 `파일경로:시작라인-끝라인` 형식.
4. 라인 확인 불가 → `확인 불가(파일경로)`.
5. 정의 못 찾음 → `찾지 못함(검색어 또는 파일경로)`.
6. 주석만 있고 구현 없음 → `주석만 존재, 구현 확인 불가`.
7. 변동 큰 설정값·외부 API·환경 변수는 "불확실"로 표시.
8. 수정 제안은 기존 로직과 비교해 설명하고 원본 로직을 임의 삭제하지 않는다.
9. 테스트/빌드/린트 명령은 프로젝트에서 실제 발견한 것만 근거와 함께 제안.

## 단계 0. 부트스트랩 (상태 파일이 없을 때)
`docs/screen-review-targets.md`가 없으면:
1. 프로젝트 구조를 분석해 "화면" 후보를 식별한다(화면 루트 폴더 단위; `*/screens/*`, `pages/`, `routes/`, `views/` 등). 각 화면이 호출하는 API/핸들러/서비스/Repo·SQL 후보를 가능한 범위에서 연결(추정은 "추정"). 화면 없는 모듈은 제외하거나 NOTES에 사유.
2. 상태 파일 초안을 자동 생성한다(부록 A 스키마). 폴더명 알파벳 순으로 `SCREEN_ID`(S001…) 부여(= 리뷰 순서), `ENTRY`에 진입점 근거(`파일:라인`), 못 찾으면 `미등록/별도 플로우 확인필요`, 모든 화면 `STATUS=PENDING`.
3. 그 회차는 리뷰하지 않고 종료(사용자 검토용).
4. 채팅에 "화면 목록 초안 생성" + 화면 개수·스택 분포 요약.
상태 파일이 있으면 단계 1로 진행.

## 단계 1. 리뷰 대상 선택 (상태 머신)
상태값: `PENDING`(대기/선택대상) · `IN_REVIEW`(진행중/건너뜀) · `DONE`(완료·PASS/건너뜀) · `NEEDS_FIX`(완료·수정필요/건너뜀) · `BLOCKED`(중단/건너뜀).
선택 규칙:
1. 위에서부터 첫 `PENDING` 1개 선택.
2. 고아 IN_REVIEW 회수: `IN_REVIEW`인데 `UPDATED_AT`이 60분 이상 지났고 보고서 파일이 없으면 `PENDING`으로 되돌려 선택 후보로.
3. 선택 즉시 `IN_REVIEW`로, `UPDATED_AT`을 현재 시각으로 갱신.
조기 종료(no-op): 선택 가능한 `PENDING`이 없으면 리뷰하지 않고 전체/`DONE`/`NEEDS_FIX`/`BLOCKED` 수 요약 + "모든 화면 리뷰 완료. 루프 중지 가능"을 출력 후 종료.

## 단계 2. 스택 감지 및 계층 매핑
선택 화면의 스택을 근거로 감지하고 계층 용어를 자동 적응시킨다.

| 일반 계층 | 웹 매핑 | 데스크톱 매핑(Qt/Delphi 등) |
|---|---|---|
| 진입/내비게이션 | Route, URL | 탭/윈도우 등록, 메뉴, 액션 시그널 |
| 뷰/컴포넌트 | 프론트 컴포넌트 트리 | 위젯/폼 트리, .ui/폼 정의 |
| 상태/입력 | store/state, 폼 검증 | 위젯 상태, 입력 검증/정규화 |
| 데이터 호출 | API client, 요청/응답 DTO | 서비스 호출, 시그널/슬롯, IPC/JSON |
| 컨트롤러/핸들러 | Controller/Handler | 이벤트 핸들러, 슬롯, 콜백 |
| 비즈니스 로직 | Service | Service/Manager/Engine |
| 데이터 접근 | Repository/Mapper/SQL | DAO, 쿼리, 파일/DB 접근 |

- 없는 계층은 발견 사항이 아니라 "해당 없음(사유)"으로 표기. 스택 단정 불가 시 `확인 불가(경로)`.

## 단계 3. 리뷰 수행 (필수 확인 항목)
스택에 맞춰 확인(없으면 "해당 없음"). 깊이가 필요하면 부록 D 사용.
1. 화면 진입 경로/내비게이션 2. 뷰·컴포넌트 구조 3. 상태/폼 검증/입력 정규화 4. 데이터 호출·요청/응답 DTO(또는 IPC/JSON) 5. 컨트롤러/핸들러/슬롯 6. 서비스/비즈니스 로직 7. 데이터 접근(Repo/Mapper/Query/SQL/파일) 8. 인증/권한/세션/토큰 9. 개인정보·민감정보·로그 노출 10. 예외 처리·오류 메시지 11. 트랜잭션·동시성·정합성 12. 성능·N+1·렌더링·캐싱·페이징·UI 블로킹 13. 테스트·누락 테스트 14. 빌드·린트·테스트 검증 명령(읽기 전용/로컬만, 결과 기록).
발견 사항은 심각도(부록 C)로 분류.

### 15. 워크플로우(교차 화면/프로세스) 추적 절차
1. 다른 화면/프로세스로 넘어가는 지점을 모두 찾는다(네비게이션 호출 `navigate`/`navigate_to`/라우팅 id/시그널, 다른 화면 위젯 직접 생성, 경계 넘는 프로세스: 인증·주문→체결·위저드·저장→재조회·콜백/딥링크).
2. 각 지점에서 대상 화면과 처리 과정(트리거→핸들러→서비스→데이터→결과/복귀)을 끝까지 추적. 순환은 1회만, `순환(이미 방문)` 표기.
3. 발견 위험(권한 누락/검증 우회/상태 불일치/토큰·세션 전달/정합성)을 보고서 "워크플로우" 섹션과 "발견 사항"에 근거와 함께 기록.
4. 따라간 화면은 상태 변경 없이 핵심 위험 1줄을 그 화면 `NOTES`에 남긴다.
5. 추적 깊이는 워크플로우 종료(최종 결과/원래 화면 복귀)까지. 무관한 공용 유틸까지 무한 확장 금지.
검증 명령은 로컬 빌드/린트/단위 테스트까지만. 외부 API 호출·DB 마이그레이션·운영 데이터 변경 금지.

## 단계 4. 보고서 작성
`docs/reviews/screens/{SCREEN_ID}-{SCREEN_NAME}.md`에 부록 B 템플릿으로 작성. `{SCREEN_NAME}`은 파일시스템 안전 슬러그(공백→`-`). 폴더 없으면 생성.

## 단계 5. 상태 갱신
`docs/screen-review-targets.md` 행 갱신:
- (주체) `STATUS`=`DONE`(PASS)/`NEEDS_FIX`/`BLOCKED` — 보고서 최종 판정과 일치
- (주체) `REVIEW_FILE`=보고서 경로, `UPDATED_AT`=현재 시각
- (추적 화면) `STATUS`는 두고 `NOTES`에 `[S0xx 워크플로우] 위험 요약` 1줄만 추가(중복 금지)
- 채팅에 변경 전/후 상태와 보고서 경로를 1줄 요약. 즉시 적용하되 변경 내역을 로그로 남긴다.
그 회차는 종료(다음 화면은 다음 루프).

## 금지 사항
- 1차 리뷰에서 소스 코드 수정 금지(문서=상태 파일·보고서만 가능).
- 파일 삭제·커밋·push·배포 금지. DB 마이그레이션·운영 데이터 변경·외부 API 호출 금지.
- 민감정보·토큰·비밀번호·개인정보·접속정보 출력 금지.
- 확인 안 한 파일·메소드·테이블·API를 단정 금지.
