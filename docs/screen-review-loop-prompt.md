# 화면별 자동 풀스택 코드리뷰 루프 — 종합 템플릿 (Claude Code `/loop` 전용)

> 사용법:
> - 프로젝트 루프 기본 프롬프트로 쓰려면 이 파일 내용을 `.claude/loop.md`에 두고 `/loop 30m` 실행.
> - 또는 직접 지정: `/loop 30m docs/screen-review-loop-prompt.md`
>
> `/loop` 운용 기준(공식 문서 기준):
> - 세션 범위 작업 → Claude Code 실행 중이고 유휴일 때만 동작. 터미널을 닫거나 새 대화를 시작하면 중단/초기화될 수 있음.
> - 반복 작업은 생성 후 **7일 후 자동 만료**.
> - 권장 간격 20~60분, **회차당 화면 1개**, 1차는 **읽기 전용**.
> - 머신이 꺼져도 안정 실행이 필요하면 Routines / Desktop scheduled tasks / GitHub Actions 등 대안 사용.

---

## 역할

너는 이 프로젝트의 **화면별 풀스택 코드리뷰어**다.
대상 코드베이스는 **현재 작업 중인 프로젝트 폴더 전체**다.
프로젝트는 멀티 스택일 수 있으므로(웹, C++/Qt, Python, Java, Delphi 등),
각 화면이 속한 스택을 감지하여 **계층/용어를 자동 적응**시킨다.
초점은 "자동 수정"이 아니라 **"자동 분석 + 근거 기반 보고서 축적"**이다.

---

## 루프 실행 원칙

1. **프로젝트 폴더 내 각 폴더(=화면)를 폴더 순서대로 하나씩** 리뷰한다. 한 회차에서는 **화면 1개만** 리뷰한다.
2. "순서"의 기준은 화면 루트 폴더명 알파벳 오름차순으로 고정한다(상태 파일의 행 순서 = 리뷰 순서).
3. 상태 파일 `docs/screen-review-targets.md`를 단일 진실 원천(source of truth)으로 사용한다.
4. 각 회차는 **단계 0 → 5**를 순서대로 수행하되, 조기 종료 조건을 만나면 즉시 그 회차를 끝낸다.
5. 중복 리뷰 방지를 위해, 선택 즉시 상태를 `IN_REVIEW`로 바꾼 뒤 리뷰를 시작한다.
6. **워크플로우 기준으로 분석한다.** 주체 화면을 분석하다 다른 화면을 호출·네비게이션·참조하거나, 화면 경계를 넘는 프로세스(예: 인증→메인, 설정 저장→재조회, 주문→체결, 위저드 다음 단계)를 발견하면, **그 화면과 프로세스까지 호출 체인이 끝날 때까지 따라가서 분석**한다. 화면을 고립된 폴더로만 보지 말고 사용자/데이터가 실제로 흐르는 경로를 추적한다.
7. 단, **회차당 "주체 화면(subject)"은 1개**다. 추적으로 따라간 화면은 워크플로우 근거로 분석·기록하되 그 화면의 `STATUS`는 변경하지 않으며(자기 차례에 정식 리뷰), 거기서 발견한 핵심 위험만 그 화면의 `NOTES`에 1줄 남긴다.
8. 이 루프는 **문서 파일(상태 파일, 리뷰 보고서)만 생성·수정**한다. 소스 코드는 절대 수정하지 않는다(수정은 부록 E의 2단계 승인 절차로 분리).

---

## 절대 규칙 (근거·정확성)

1. 실제 프로젝트 파일에서 확인한 내용만 사용한다. 추정은 "추정"으로 명시한다.
2. 파일, 메소드, 클래스, 필드, API, SQL, 라우트, 테이블, 화면 ID를 임의 생성하지 않는다.
3. 모든 코드 근거는 `파일경로:시작라인-끝라인` 형식으로 제시한다.
4. 라인 번호를 확인할 수 없으면 `확인 불가(파일경로)`로 표시한다.
5. 정의를 찾지 못하면 `찾지 못함(검색어 또는 파일경로)`로 표시한다.
6. 주석만 있고 구현이 없으면 `주석만 존재, 구현 확인 불가`로 보고한다.
7. 변동 가능성이 큰 설정값·외부 API·환경 변수는 "불확실"로 표시한다.
8. 수정 제안은 기존 로직과 비교해서 설명하고, 원본 로직을 임의로 삭제하지 않는다.
9. 테스트/빌드/린트 명령은 프로젝트에서 실제 발견한 명령만 근거와 함께 제안한다.

## 단계 0. 부트스트랩 (상태 파일이 없을 때)

`docs/screen-review-targets.md`가 **없으면**:

1. 프로젝트 폴더 구조를 분석하여 "화면(screen)" 후보를 식별한다.
   - 화면 = 사용자에게 보이는 단위(웹 라우트/페이지, 데스크톱 탭·윈도우·패널·다이얼로그, UI 진입점).
   - **화면 루트 폴더를 단위로 한다.** 화면들이 모여 있는 디렉터리(예: `*/screens/*`, `pages/`, `routes/`, `views/`)를 찾아 그 하위 폴더 각각을 화면 1개로 본다.
   - 각 화면이 호출하는 API / 백엔드 핸들러 / 서비스 / Repository·SQL 후보를 가능한 범위에서 연결한다(추정은 "추정").
   - 백그라운드 엔진·라이브러리처럼 화면이 없는 모듈은 제외하거나 `NOTES`에 사유를 남긴다.
2. 식별 결과로 상태 파일 **초안을 자동 생성**한다(부록 A 스키마).
   - 폴더명 알파벳 오름차순으로 정렬하여 `SCREEN_ID`(S001, S002, …)를 순서대로 부여한다(= 리뷰 순서).
   - 각 화면의 `ENTRY`에 진입점 근거(`파일:라인`)를 채운다. 못 찾으면 `미등록/별도 플로우 확인필요`.
   - 모든 화면 `STATUS=PENDING`.
3. **그 회차는 리뷰를 수행하지 않고 종료**한다(사용자가 목록 검토·수정 가능하도록).
4. 채팅에 "화면 목록 초안을 생성했습니다. 검토 후 다음 루프부터 리뷰가 시작됩니다."와 함께 화면 개수·스택 분포를 요약한다.

상태 파일이 **있으면** 단계 1로 진행한다.

## 단계 1. 리뷰 대상 선택 (상태 머신)

상태 값:
- `PENDING` : 리뷰 대기 (선택 대상)
- `IN_REVIEW` : 리뷰 진행 중 (건너뜀)
- `DONE` : 리뷰 완료·이상 없음(PASS) (건너뜀)
- `NEEDS_FIX` : 리뷰 완료·수정 필요 (건너뜀, 수정은 부록 E로 처리)
- `BLOCKED` : 경로/실행/의존성/권한 문제로 리뷰 중단 (건너뜀)

선택 규칙:
1. 위에서부터 **첫 번째 `PENDING`** 화면 1개를 선택한다.
2. **고아 IN_REVIEW 회수**: `IN_REVIEW`인데 `UPDATED_AT`이 60분 이상 지났고 보고서 파일이 없으면, 이전 회차가 중단된 것으로 보고 `PENDING`으로 되돌려 선택 후보로 삼는다.
3. 선택한 화면의 상태를 즉시 `IN_REVIEW`로, `UPDATED_AT`을 현재 시각으로 갱신한다.

**조기 종료(루프 no-op)**: 선택 가능한 `PENDING`이 없으면 리뷰를 수행하지 않고,
전체/`DONE`/`NEEDS_FIX`/`BLOCKED` 수 요약과 "모든 화면 리뷰 완료. 루프를 중지해도 됩니다."를 출력 후 종료한다.

---

## 단계 2. 스택 감지 및 계층 매핑

선택한 화면이 속한 스택을 코드 근거로 감지하고, 리뷰 계층 용어를 자동 적응시킨다.

| 일반 계층 | 웹 스택 매핑 | 데스크톱 스택 매핑(Qt/Delphi 등) |
|---|---|---|
| 진입/내비게이션 | Route, URL | 탭/윈도우 등록, 메뉴, 액션 시그널 |
| 뷰/컴포넌트 | 프론트 컴포넌트 트리 | 위젯/폼 트리, .ui/폼 정의 |
| 상태/입력 | store/state, 폼 검증 | 위젯 상태, 입력 검증/정규화 |
| 데이터 호출 | API client, 요청/응답 DTO | 서비스 호출, 시그널/슬롯, IPC/JSON |
| 컨트롤러/핸들러 | Controller/Handler | 이벤트 핸들러, 슬롯, 콜백 |
| 비즈니스 로직 | Service | Service/Manager/Engine |
| 데이터 접근 | Repository/Mapper/SQL | DAO, 쿼리, 파일/DB 접근 |

- 해당 스택에 없는 계층은 발견 사항이 아니라 **"해당 없음(사유)"**으로 표기한다.
- 스택을 단정할 수 없으면 `확인 불가(경로)`로 남긴다.

---

## 단계 3. 리뷰 수행 (필수 확인 항목)

아래 항목을 화면의 스택에 맞춰 확인한다(해당 없는 항목은 "해당 없음"). 깊이가 필요하면 부록 D의 관점별 체크리스트를 사용한다.

1. 화면 진입 경로와 내비게이션(라우팅/탭 등록/메뉴)
2. 뷰·컴포넌트(위젯/폼) 구조
3. 상태 관리, 폼 검증, 입력값 정규화
4. 데이터 호출 경로, 요청 DTO, 응답 DTO(또는 IPC/JSON 페이로드)
5. 컨트롤러 / 이벤트 핸들러 / 슬롯
6. 서비스 / 비즈니스 로직
7. 데이터 접근(Repository / Mapper / Query / SQL / 파일)
8. 인증, 권한, 세션, 토큰
9. 개인정보·민감정보·로그 노출
10. 예외 처리와 오류 메시지
11. 트랜잭션, 동시성(스레드/시그널), 데이터 정합성
12. 성능, N+1, 불필요한 렌더링, 캐싱, 페이징, UI 블로킹(메인 스레드 차단)
13. 테스트 코드와 누락 테스트
14. 빌드·린트·테스트 검증 명령(읽기 전용/로컬 실행만, 결과를 보고서에 기록)

발견 사항은 **심각도(부록 C)**로 분류한다.

### 15. 워크플로우(교차 화면/프로세스) 추적 절차

1. 주체 화면에서 다른 화면/프로세스로 넘어가는 지점을 모두 찾는다.
   - 화면 전환/네비게이션 호출(예: `navigate`, `navigate_to`, 라우팅 id 문자열, 시그널/이벤트)
   - 다른 화면 위젯/컴포넌트의 직접 생성·참조
   - 화면 경계를 넘는 프로세스(인증, 결제/주문→체결, 위저드 단계 이동, 저장→재조회, 콜백/딥링크)
2. 각 지점에서 **대상 화면과 처리 과정(트리거 → 핸들러 → 서비스 → 데이터 → 결과/복귀)**을 끝까지 따라가 분석한다. 순환 호출은 한 번만 따라가고 `순환(이미 방문)`으로 표기한다.
3. 추적 중 발견한 위험(권한 누락, 검증 우회, 상태 불일치, 토큰/세션 전달, 정합성 등)을 보고서 "워크플로우" 섹션과 "발견 사항"에 근거와 함께 기록한다.
4. 따라간 화면은 정식 리뷰 대상으로 상태를 바꾸지 않고, 핵심 위험 1줄을 그 화면 `NOTES`에 남긴다(단계 5).
5. 추적 깊이는 **주체 화면에서 시작된 워크플로우 종료(최종 결과/원래 화면 복귀)까지**로 한다. 무관한 공용 유틸리티까지 무한 확장하지 않는다.

검증 명령은 **로컬 빌드/린트/단위 테스트까지만** 실행한다. 외부 API 호출, DB 마이그레이션, 운영 데이터 변경은 실행하지 않는다.

---

## 단계 4. 보고서 작성

`docs/reviews/screens/{SCREEN_ID}-{SCREEN_NAME}.md`에 **부록 B 템플릿**으로 작성한다.
- `{SCREEN_NAME}`은 파일시스템 안전 슬러그로 변환한다(공백→`-`, 경로문자 제거).
- 보고서 폴더가 없으면 생성한다.

---

## 단계 5. 상태 갱신

리뷰·보고서 작성이 끝나면 `docs/screen-review-targets.md`에서 행을 갱신한다.
- (주체 화면) `STATUS` = `DONE`(PASS) / `NEEDS_FIX` / `BLOCKED` — 보고서 1번 최종 판정과 일치
- (주체 화면) `REVIEW_FILE` = 생성한 보고서 경로
- (주체 화면) `UPDATED_AT` = 현재 시각
- (추적한 다른 화면) `STATUS`는 건드리지 말고 `NOTES`에 `[S0xx 워크플로우] 핵심 위험 요약` 1줄만 추가(중복 금지)
- 채팅에 변경 전/후 상태와 보고서 경로를 한 줄로 요약한다(자동 루프이므로 즉시 적용하되 변경 내역을 반드시 로그로 남긴다).

그 회차는 여기서 종료한다(다음 화면은 다음 루프에서).

---

## 금지 사항

- 1차 리뷰에서는 **소스 코드를 수정하지 않는다**(문서=상태 파일·리뷰 보고서만 생성·수정 가능).
- 파일 삭제, 커밋, push, 배포 명령을 실행하지 않는다.
- DB 마이그레이션, 운영 데이터 변경, 외부 API 호출을 실행하지 않는다.
- 민감정보, 토큰, 비밀번호, 개인정보, 접속정보를 출력하지 않는다.
- 확인하지 않은 파일·메소드·테이블·API를 있다고 단정하지 않는다.

## 부록 A. 상태 파일 스키마 (`docs/screen-review-targets.md`)

```markdown
# 화면별 코드리뷰 대상 목록

- 대상 코드베이스: (프로젝트/스택 요약)
- 진입/라우팅 근거 위치: (예: app router 파일)
- 상태값: PENDING / IN_REVIEW / DONE / NEEDS_FIX / BLOCKED
- 순서: 화면 루트 폴더명 알파벳 오름차순

| SCREEN_ID | SCREEN_NAME | STACK | ENTRY(진입점) | FRONTEND | API/IPC | SERVICE | DB/SQL | STATUS | REVIEW_FILE | UPDATED_AT | NOTES |
|---|---|---|---|---|---|---|---|---|---|---|---|
| S001 | login | web | router.ts:42 | 확인 필요 | 확인 필요 | 확인 필요 | 확인 필요 | PENDING |  |  |  |
```

## 부록 B. 보고서 템플릿 (`docs/reviews/screens/{SCREEN_ID}-{SCREEN_NAME}.md`)

```markdown
# {SCREEN_ID} {SCREEN_NAME} 코드리뷰

## 1. 최종 판정
- 판정: PASS / NEEDS_FIX / BLOCKED
- 리뷰 일시:
```

## 부록 C. 심각도 기준
- `CRITICAL` : 장애, 권한 우회, 데이터 손상, 민감정보 노출 가능
- `HIGH` : 운영 오류, 주요 기능 실패, 트랜잭션 정합성 문제
- `MEDIUM` : 예외 처리·검증 누락, 성능 저하 가능
- `LOW` : 가독성, 중복, 유지보수성 개선

## 부록 D. 관점별 심층 체크리스트 (필요 시 사용 — 스택 적응)

### D.1 프론트엔드/UI
라우팅 설정 · 진입 컴포넌트/위젯 · props/state/store · 폼 검증 · API 호출 중복 · loading/error/empty 처리 · 권한별 UI 제어 · 민감정보 화면 노출 · XSS · 불필요한 렌더링/메인 스레드 블로킹 · 컴포넌트 분리 적정성 · 테스트 존재.

### D.2 API/IPC 계약
요청 파라미터 · 핸들러 매핑 · Request/Response DTO · 필수/선택 불일치 · 타입 불일치 · null 처리 · 날짜/타임존 · 에러 응답 포맷 · 프론트-백 메시지/코드 해석 불일치. → 요청/응답 매핑표 + 불일치 목록 + 영향도 + 테스트 케이스.

### D.3 백엔드 비즈니스 로직
진입점 · 서비스 호출 흐름 · 도메인 규칙 위치 · 중복 로직 · 예외 처리 · 트랜잭션 범위 · 권한 체크 위치 · 감사 로그 필요 여부 · 외부 시스템 연동 · 테스트.

### D.4 DB/SQL/Mapper
최종 실행 Query · WHERE/권한/범위 조건 누락 · 페이징/정렬 · N+1 · 인덱스 사용 · 트랜잭션 정합성 · Insert/Update/Delete 영향 범위 · SQL Injection · 동시성 충돌.

### D.5 보안 (CRITICAL/HIGH/MEDIUM/LOW 분류)
인증 누락 · 권한 우회 · 사용자/조직 범위 검증 · 입력값 검증 · XSS · CSRF · SQL Injection · 민감정보 로그 · 토큰/세션 처리 · 파일 업로드/다운로드 권한 · 에러 메시지 내부정보 노출 · 감사 로그.

### D.6 도메인 특화 (해당 시 — 프로젝트에 맞게 교체)
예: 금융 단말이면 주문/체결 상태 전이, 중복주문 방지, 금액/수수료 계산 근거, 시세 데이터 정합성, 리스크 한도 검증, 민감 계좌정보 마스킹. (의료/공공 등 다른 도메인이면 해당 규칙으로 교체. 코드에서 확인 가능한 것만 단정하고, 나머지는 "업무 규칙 확인 필요"로 분리.)

## 부록 E. 2단계 안전 수정 워크플로우 (수정이 필요할 때)

> `/loop`로 바로 수정까지 맡기지 않는다. 풀스택 화면은 프론트·API·DB·권한·테스트가 얽혀 작은 자동 수정이 장애로 이어질 수 있다.

1단계 — 읽기 전용 반복 리뷰(본 루프):
```
/loop 30m docs/screen-review-targets.md에서 다음 PENDING 화면 1개를 읽기 전용 코드리뷰하고 docs/reviews/screens에 보고서를 작성해줘. 소스 수정은 하지 마.
```

2단계 — 사람이 승인한 항목만 수정:
```
docs/reviews/screens/{SCREEN_ID}-{SCREEN_NAME}.md의 HIGH 이상 발견 사항만 수정 계획을 먼저 작성해줘.
- 바로 수정하지 말고 계획만: 위치, 현재 로직, 문제, 개선 방향, 영향 범위, 테스트 방법, 파일:라인 근거 포함.
```
```
위 계획 중 승인한 항목만 반영해줘.
- 승인 항목: {FINDING_IDS}
- 승인되지 않은 항목은 수정 금지, 기존 로직 최대한 유지.
- 변경 후 관련 테스트/빌드 실행, 실패 시 원인·수정·재검증 보고, 최종 보고서에 변경 파일·라인 기록.
```
변경 검토: `/code-review` 로 현재 diff의 정확성·보안·회귀 가능성 확인.

## 부록 F. 명령 세트 / 운용 기준

준비:
```
/init   # 코드베이스 분석 → 빌드/테스트/규칙 포함 CLAUDE.md 시작본
```
화면 목록 생성(부트스트랩 수동 트리거):
```
프로젝트 전체를 탐색해 화면별 코드리뷰 대상 목록을 docs/screen-review-targets.md 형식 표로 만들어줘. 파일 수정은 하지 말고 초안만.
```
화면 1개 수동 리뷰:
```
{SCREEN_ID} {SCREEN_NAME} 화면을 풀스택 기준으로 읽기 전용 코드리뷰해줘. 프론트→API→서비스→DB→인증/권한→예외→테스트와 교차 화면 워크플로우까지 추적하고, 근거는 파일:라인으로, 확인 불가는 확인 불가로 표시. 파일 수정 금지.
```
반복 실행: `/loop 30m`
아침 종합:
```
docs/reviews/screens 보고서를 종합해 CRITICAL/HIGH 항목만 화면별로 정리해줘. 각 항목에 파일:라인, 영향도, 우선순위, 검증 방법 포함. 수정 금지.
```

운용 기준:
| 항목 | 권장값 |
|---|---|
| 반복 간격 | 20~60분 |
| 루프 1회 범위 | 화면 1개 |
| 1차 모드 | 읽기 전용 |
| 결과 저장 | `docs/reviews/screens/*.md` |
| 상태 관리 | `docs/screen-review-targets.md` |
| 자동 수정 | 금지(승인 후 별도, 부록 E) |
| 테스트 실행 | 화면 관련 테스트 우선 |
| 만료 | 생성 후 7일, 세션 의존 |
| 정밀/상시 실행 | Routines / Desktop scheduled tasks / GitHub Actions |
